# 用 Notion 當系統資料庫的建置規則

Notion 拿來當應用系統的資料庫是可行的，但它不是關聯式資料庫——沒有 row-level security、沒有交易、沒有唯一鍵約束，而且 API 限速很低。這份規則把踩過的坑固化成流程。

**最適合的情境**：資料量小（單表數百至數千筆）、變動頻率低（一天數次到一個月數次）、需要非工程人員能直接在 Notion 介面查看與修改。

**不適合**：高頻寫入、需要交易一致性、需要複雜 JOIN、單表破萬筆。這些情況請改用 Supabase / Postgres。

---

## 一、核心架構：單一 Page + 前綴詞

**所有系統的資料表都放在同一個 Notion Page 底下，以前綴詞區分歸屬。**

```
📄 系統資料庫（單一 Page）
   ├── 培訓・使用者      ← A 系統
   ├── 培訓・成績
   ├── 導師・使用者      ← B 系統
   ├── 導師・學生
   └── 導師・稽核日誌
```

命名格式：`{系統前綴}・{資料表名}`，分隔符用全形間隔號 `・`（不易與資料內容混淆）。

**為什麼這樣做**

- 一個 Notion 整合權杖、一個 Page ID 就能服務所有系統，不必為每個系統維護一組環境變數
- 新增資料表不需要改環境變數或重新部署——程式啟動時掃描該 Page，用前綴篩出屬於自己的表
- 在 Notion 介面上所有系統的表排在一起，管理集中

**程式端只需要兩個環境變數**

```
NOTION_TOKEN=ntn_xxx
NOTION_ROOT_PAGE_ID=<32碼十六進位>
NOTION_TABLE_PREFIX=導師・        # 可選，寫死在程式裡也行
```

探索流程：`blocks.children.list(rootPageId)` → 取出 `child_database` 類型的區塊 → 用 `block.child_database.title` 比對前綴 → 後綴對應到邏輯表名。快取 60 分鐘。

## 二、建置流程

### 步驟 1：先定資料模型，再建表

在動手建表之前先把這幾件事寫清楚，否則建完才發現要改欄位很麻煩：

- 每張表的**主鍵格式**（Notion 的 title 欄位就是主鍵，要自己設計唯一格式）
- 哪些表帶**權限邊界欄位**（多租戶／多班級／多部門系統必備）
- 哪些欄位是**敏感個資**（要加密）
- 哪些欄位會**超過 2000 字元**（要分段存）

### 步驟 2：主鍵格式設計

Notion 沒有自動遞增 ID，也不會擋重複值。主鍵要自己組成「人看得懂 + 保證唯一」的格式：

| 情境 | 格式 | 範例 |
|---|---|---|
| 隸屬某個範圍的實體 | `{範圍ID}-{序號補零}` | `114-資訊二真-01` |
| 單例（每個範圍一筆） | `{範圍ID}-{表名}` | `114-資訊二真-座位表` |
| 流水記錄 | `{範圍ID}-{類型碼}{流水號}` | `114-資訊二真-A0012` |
| 時序日誌 | `{ISO時間戳}-{序號}` | `2026-08-28T14:30:00Z-0001` |

寫入前一律先查是否已存在，Notion 不會幫你擋。

### 步驟 3：用 SQL DDL 建表

Notion MCP 的 `create-database` 接受 CREATE TABLE 語法，比一個一個點介面快得多，也比較不會漏欄位。

```sql
CREATE TABLE (
  "學生KEY" TITLE COMMENT '格式：班級ID-座號補零2位',
  "班級ID" RICH_TEXT COMMENT '權限邊界，由系統寫入',
  "座號" NUMBER,
  "姓名" RICH_TEXT,
  "家長電話" RICH_TEXT COMMENT '🔒 加密欄位，密文為正常現象',
  "狀態" SELECT('正常':green, '已刪除':red),
  "版本" NUMBER COMMENT '樂觀鎖',
  "刪除時間" DATE
)
```

**每個欄位都加 `COMMENT`**。這些說明會顯示在 Notion 介面的欄位提示上，之後別人（或半年後的你）在 Notion 看到密文欄位才知道那是正常的，不會手動去「修正」它。

詳細語法與各型別範例見 [references/ddl-cookbook.md](references/ddl-cookbook.md)。

### 步驟 4：建完立刻用程式驗證

不要相信「建好了」，要讓程式自己掃一次，確認每張表都找得到、欄位型別對得上。做一支 `/api/health` 之類的診斷端點回報：

- 找到的資料表 / 缺少的資料表
- 前綴符合但名稱不認得的表（表示有人手動改名了）
- 加密往返測試是否通過
- Root Page 是否被設為公開分享

這支端點之後會變成管理者介面的「資料庫狀態」頁，不是一次性的工具。

## 三、五個結構決策

### 1. 權限邊界用純文字欄位，不用 relation

多租戶系統（每位導師只能看自己班、每個部門只能看自己部門）需要一個欄位標示歸屬。

**用 `RICH_TEXT` 存範圍 ID，不要用 Notion relation。** relation 的 filter 支援較弱、需要額外請求解析、寫起來容易漏。純文字的 `rich_text: { equals: "..." }` 過濾單純、效率高、不易寫錯。

### 2. 高格數資料存單筆 JSON，不要一格一筆

座位表 6×6 = 36 格、課表 5 天×8 節 = 40 格。如果一格一筆 Notion record，儲存一次要打 36 次 API，以 3 req/s 算要 12 秒。

**改成整張表存成一個 JSON 欄位，一次寫入完成。**

```
配置JSON: [[4,7,13,22,14],[null,3,18,9,27],...]    ← 值是座號，null 是空位
```

判斷準則：這批資料**總是一起讀、一起寫**，而且**不需要對單格做查詢或排序** → 存 JSON。反之（例如每筆要獨立查詢、要按日期排序）→ 一筆一列。

### 3. 長文字要分段存

Notion 單一 rich_text object 的 content 上限 **2000 字元**，但一個 property 可以放最多 **100 個 rich_text object** → 實際容量約 180,000 字元。

超過 1800 字元就自動切段寫入，讀取時把所有 `plain_text` 串接還原。封裝成 `readJsonProp()` / `writeJsonProp()` 共用工具，不要每個地方各寫一份。

### 4. 敏感個資必須加密後才寫入

Notion 頁面一旦誤設公開分享就是全網可讀，而且分享連結無法稽核。姓名、電話、身分證號、輔導紀錄、健康狀況這類欄位：

- 寫入前 **AES-256-GCM** 加密，格式 `enc:v1:{base64(iv)}:{base64(ciphertext+tag)}`
- 金鑰放環境變數，**絕不進版控**
- 加解密只在資料存取層做，其他地方不碰
- 帶版本前綴（`v1`/`v2`）以支援金鑰輪替

**識別性欄位（姓名、編號、範圍ID）保持明文**，否則你在 Notion 介面完全認不出在看哪一筆，等於白用 Notion。這是刻意的取捨：可辨識 vs 完全不可讀。

⚠️ 金鑰遺失 = 資料永久無法解密。正式環境的金鑰務必另行備份。

### 5. 不做實體刪除

- 一般資料：`狀態` 改為 `已刪除` + 記 `刪除時間`，進回收桶，保留 N 天後才由管理者永久刪除
- **金錢類分錄：完全不可修改、不可刪除**。更正方式是新增一筆反向分錄並標註「沖銷對象」，原分錄狀態改「已沖銷」。餘額由狀態正常的分錄計算

Notion API 的「刪除」其實是 `in_trash: true`（封存），Notion 垃圾桶仍保留 30 天，等於多一層保險。

## 四、每個系統都該有的四張表

不管做什麼系統，這四張建了就不會後悔：

| 表 | 用途 | 關鍵欄位 |
|---|---|---|
| `{前綴}・使用者` | 帳號、角色、授權範圍 | 帳號(title)、角色、授權範圍(multi_select)、狀態、登入失敗次數、鎖定至 |
| `{前綴}・密碼` | argon2id 雜湊 | 帳號(title)、雜湊、更新時間 |
| `{前綴}・系統設定` | 所有可調參數 | 設定KEY(title)、範圍ID、設定值、型別、說明 |
| `{前綴}・稽核日誌` | 所有異動紀錄 | 日誌KEY(title)、時間、操作者、動作、目標表、目標KEY、變更內容、IP |

**密碼表**：只存 argon2id 雜湊（`memoryCost=19456, timeCost=2, parallelism=1`），永不回傳前端、永不寫進稽核日誌。

**系統設定表**：任何「將來可能要調」的東西都放這裡——下拉選單的選項清單、門檻值、預設值。程式裡出現 `const 選項 = ['A','B','C']` 就是錯的。改設定不該需要重新部署。

**稽核日誌**：敏感欄位的變更**只記「已變更」，不記新舊值**，否則稽核日誌會變成個資外洩的第二個入口。

## 五、程式端的四件必要工程

### 1. 唯一資料存取層

所有 Notion 呼叫集中在一個 `repository` 模組，其他地方一律不得 import Notion SDK。權限檢查、加解密、節流、快取、稽核都只在這一層實作一次。繞過它 = 所有防護失效。

### 2. 權限隔離三道防線

Notion **沒有** row-level security。多租戶隔離完全靠程式：

| 防線 | 做法 |
|---|---|
| 讀取 | 查詢強制附加 `範圍ID = session.範圍ID`。前端不傳，傳了也忽略 |
| 新增 | 寫入的 `範圍ID` 由 session 覆蓋，不採用 request body 的值 |
| 修改／刪除 | **先讀取目標記錄比對範圍ID，不符回 403**，通過才寫入 |

第三道最容易漏。只靠前端不顯示別人的資料是不夠的——改一下 request 裡的 record key 就能動到別人的。

「找不到」與「存在但無權限」都回 **404**，不要區分，否則能用回應差異推測資料是否存在。

### 3. 集中式節流佇列

Notion 限速約 **3 req/s，而且是整個整合共用**，不是每個使用者 3 次。所有請求排進單一佇列以 2.5 req/s 送出，429 採指數退避重試最多 3 次。

**不要用 `Promise.all` 平行呼叫 Notion**——那不會變快，只會讓某個人的批次操作把其他人全部卡住，還容易撞 429。

### 4. 分層快取

| 對象 | TTL |
|---|---|
| 資料表清單、欄位定義 | 60 分鐘 |
| 名單類資料 | 10 分鐘 |
| 高變動資料 | 5 分鐘 |
| 稽核日誌 | 不快取 |

**快取 key 必須包含權限範圍 ID**，否則會發生跨租戶污染——A 讀到 B 的資料。寫入後主動失效。

## 六、Notion API 陷阱

| 陷阱 | 說明 |
|---|---|
| `databases.query` 已移除 | SDK v5 / API 2025-09 起改用 `dataSources.query`。流程是 database → data_sources[0].id → 查詢 |
| 建立頁面的 parent | `{ type: 'data_source_id', data_source_id }`，不是 `database_id` |
| rich_text 2000 字元 | 單一 object 上限，超過要切段 |
| multi_select 會自動建選項 | 寫入不存在的選項值時 Notion 會自動建立。方便，但也表示打錯字不會報錯 |
| multi_select 選項不是資料來源 | 前端下拉選單要從**實際的主檔表**讀，不要讀 multi_select 的既有選項——那是「曾被寫入過的值」，會混入錯字與已失效的項目 |
| select vs status | 兩者的 filter 語法不同。程式要依 Notion 上的實際型別決定轉換方式，不要寫死 |
| 沒有唯一鍵 | 主鍵重複 Notion 不會擋，要自己先查 |
| 沒有交易 | 多筆寫入中途失敗會留下不一致狀態。盡量設計成單筆寫入完成一件事 |
| 分頁 | 查詢預設 100 筆，`has_more` 為 true 時要帶 `start_cursor` 續抓 |

## 七、建置檢查清單

建完一套 Notion 資料庫後逐條確認：

- [ ] 所有表都以系統前綴命名，且在同一個 Root Page 底下
- [ ] 每個欄位都有 `COMMENT` 說明，敏感欄位標了 🔒
- [ ] 程式能掃描到全部資料表，缺少清單為空
- [ ] 主鍵格式唯一且人看得懂
- [ ] 敏感欄位實際查詢 Notion 確認是密文（不要只相信程式回報）
- [ ] 識別性欄位維持明文，在 Notion 介面認得出是哪一筆
- [ ] 用另一個租戶／範圍的記錄 KEY 呼叫修改 API，確認回 403/404
- [ ] 前端 bundle 搜尋不到任何金鑰
- [ ] Root Page 未被設為公開分享，且系統有自動檢查
- [ ] `.env*` 在 `.gitignore` 裡，`git log` 中無金鑰
- [ ] 高格數資料（座位表、課表之類）是單筆 JSON 而非一格一筆
- [ ] 快取 key 含範圍 ID
- [ ] 系統設定表已建立，程式中沒有寫死的選項清單
