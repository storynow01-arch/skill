# 開工 / 收工 工作階段管理

這是使用者個人的工作習慣,不是特定專案的規則。任何專案資料夾裡,只要使用者說「開工」或「收工」,都要照這裡的流程走——即使該專案沒有為此寫過任何說明。

核心理念:交接文件是給「下一個對話的自己」看的。開工時把它當作可能過期的參考,動手核對;收工時把它寫得讓下一個對話不用重新調查一次就能接手。

## 開工流程

1. **找交接文件**。依序嘗試:
   - 專案根目錄的 `CLAUDE.md` 或 `AGENTS.md` 裡有沒有明講「先讀哪份文件」(很多專案會這樣指定,例如 `HANDOFF.md`)。
   - 專案根目錄常見檔名:`HANDOFF.md`、`STATUS.md`、`PROGRESS.md`、`HANDOFF.zh-TW.md` 之類的變體。
   - 都找不到,就當作這個專案還沒有這個習慣,跳到步驟 4。

2. **讀完整份文件**,特別留意開頭的「目前狀態 / 最後更新」區塊和底部的「進度日誌」。

3. **驗證,不要照單全收**。文件裡任何描述「外部世界目前狀態」的句子(伺服器是否在跑、是否部署成功、目前分支、密碼是否有效、IP 位址、某個服務是否還連著)都可能在文件寫完之後就過期了。花點時間動手確認:
   - 伺服器/process:實際檢查 process 或連 port(如 `curl localhost:PORT`、`Get-NetTCPConnection`)。
   - git 狀態:`git status`、`git log`、`git branch -vv`,不要相信文件說「已經 push」就不查。
   - 部署狀態:如果文件提到某個網址,花一次請求驗證還活著。
   之所以要驗證,是因為這類文件通常是「上次收工當下」的快照,而環境會在對話之間漂移(IP 換了、密碼被重設、服務被手動重啟過),盲信舊快照容易做出根據錯誤前提的決定。

4. **順手確認 `.env` 類機密檔有被 `.gitignore` 排除**。如果專案有 `.env` / `.env.local` / 金鑰檔,花一秒確認它們在 `.gitignore` 裡(`git check-ignore .env.local` 或看 `.gitignore` 內容)。這是開工時最低成本的資安檢查,防止後面不小心把金鑰 commit 上去——與其收工才發現外洩,不如開工就確認防線在。

5. **動手確認執行環境與隔離狀態（絕不污染全域環境）**：
   - Python 專案：動手確認執行的 `python` 或 `uv` 是否確實指向專案內的虛擬環境（`.venv`），**嚴禁使用系統 base 環境或單獨使用全域 pip**，絕不弄髒環境。
   - Node / 前端專案：確認 `node_modules` 與核心套件（例如 `@remotion/paths`）是否存在且完好。

6. **輸出「3 秒現況儀表板」向使用者簡報**：
   驗證完成後，以極簡短的 3~4 行格式向使用者回報，不長篇大論，讓使用者在 2 秒內確認接軌狀態：
   > 🌅 **開工確認**  
   > • 接手文件：`[檔名]`（環境驗證：.venv 隔離正常、git clean、無敏感外洩）  
   > • 當前現況：`[1 句核心狀態摘要]`  
   > • 本次預計：`[具體下一步動作]`  
   > • 請問立即開始嗎？

7. **開始做事**時依文件裡記載的架構原則、既有慣例進行,不要無視既有做法另起爐灶。如果這個專案根本沒有交接文件,就正常開始工作,不用刻意為了套用這個習慣而多問。

## 收工流程

1. **整理這次對話做的事**,寫成摘要,涵蓋:
   - 做了什麼,以及**為什麼這樣做**(動機、使用者的原始需求、當下的決策理由)。記「為什麼」通常比記「做了什麼」更有價值——程式碼本身會說明「做了什麼」,但「為什麼選 A 不選 B」只存在腦袋裡,不寫下來下一個對話就得重新推導甚至推翻。
   - 過程中遇到並解決的問題(尤其是任何「後來才發現的根因」,這種最值得留給未來的自己)。
   - 還沒做完的、下一步該做的事。**「下一步」要寫成可直接執行的指示**:具體到指令、檔名、行號、函式名,而不是「繼續優化 UI」「把資料補齊」這種模糊句。
   - **【煞車點決策樹】**：若下一步涉及「煞車點（⛔ 人工決策）」或多選一方案，寫成「決策樹指示」而非單一死指令（例如：`【待決策煞車點】等待使用者確認 [決策項目]：若選 A 則執行...；若選 B 則執行...`），防止下一個對話的 AI 略過使用者詢問而擅自做主。

2. **寫回交接文件的進度日誌**。找到文件裡類似「進度日誌」「Changelog」「工作紀錄」的區塊(通常在檔案底部,新的在最上面),照著既有的格式、日期慣例、語氣加一條新紀錄。沒有進度日誌區塊的話,在文件末尾新增一個,並維持這個格式讓以後好接續。

3. **同步更新現況摘要**。如果這次對話讓文件開頭「目前狀態」區塊描述的東西變了(部署網址、伺服器是否在跑、密碼、IP、分支狀態、剛解決或剛發現的問題),把那個區塊也一起改掉,而不是只加日誌——這是為了讓下一次「開工」不用重新調查就能拿到正確現況,呼應開工流程裡「驗證」這步的精神:這次好好更新,下次就少一次要驗證的落差。

   **絕對不要把真正的密碼、API key、token、連線字串等機密值寫進交接文件。** 這類文件通常會被 commit 進 git、甚至是公開或多人看得到的 repo。需要提到「密碼被重設了」這件事時,寫**存放位置**(例如「新密碼在 xxx.txt,不在 git 裡」)或**做了什麼動作**,不要寫值本身。如果懷疑某個要寫進日誌的內容可能是機密,先假設它是,換成指向位置的說法。

4. **如果這次動了程式,確認留下的是「可運行狀態」**。收工前跑一次專案的建置/測試(例如 `npm run build`、`npm test`、type check,依專案而定),確保沒有把編譯錯誤、壞掉的測試、半完成的重構丟給下一個對話。如果因故沒辦法留在可運行狀態(例如做到一半、刻意留個 TODO),就在進度日誌裡**明講「目前是壞的、壞在哪、怎麼繼續」**,不要讓下一個對話開工後才踩到。這呼應開工流程的「驗證」精神:你這次確保可運行,下次開工就少一個要救火的坑。

5. **暫存與產物盤點清理**：
   - 標明本次產出的「最終交付檔案路徑」（例如 `out/` 或正式成品）。
   - 清理或宣告暫存快取（如渲染臨時 frames、測試音訊、tmp 檔），避免無效膨脹磁碟或干擾下一個對話開工。

6. **收工掃一次這次的改動有沒有寫死機密**。對這次新增/修改的檔案做一次掃描(`git diff` 看改了什麼,再用關鍵字搜尋 `API_KEY|SECRET|PASSWORD|TOKEN|BEGIN .*PRIVATE KEY`、以及 `postgres://`、`sk-`、`sb_secret` 這類連線字串/金鑰前綴),確認沒有把真正的密鑰硬編碼進程式或設定檔。機密該走環境變數(`.env` / `.env.local`,且已被 gitignore),不該出現在會進 git 的檔案裡。**要 commit 時尤其要先做這步**——密鑰一旦進了 git 歷史,事後很難乾淨移除。注意「設計上就要公開的」金鑰(如前端 publishable key、`NEXT_PUBLIC_*`)是例外,那類本來就會打包進前端,重點是抓「真正的 secret」。

7. **只改檔案內容,不要自己 commit / push**。除非使用者在同一句話裡明確一併要求(例如「收工,順便 commit」),兩者才會一起做。單純說「收工」時,commit 與否要留給使用者決定。

8. 找不到交接文件的專案,收工時可以主動問使用者要不要建一份(尤其如果這次對話做的事不小,值得留紀錄),但不要自作主張硬幫使用者建立一份陌生格式的文件——先問一句。
